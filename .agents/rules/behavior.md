# 行为准则

源自 Andrej Karpathy 对 LLM 编码陷阱的观察，约束 AI 的**工作方式**（HOW），与领域规则（WHAT）互补。

**权衡：** 这些准则偏向谨慎而非速度。对于简单任务（拼写错误、明显的一行修复），自行判断——并非每次改动都需要完整流程。

---

## 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

动手之前：

- 明确陈述你的假设。如果不确定，直接问。
- 如果存在多种理解，全部列出来——不要默默选择一种。
- 如果有更简单的方案，说出来。该反驳时反驳。
- 如果有不清楚的地方，停下来。指出困惑点。提出疑问。
- 接口路径 / 字段不确定时，先查 **blue-dock-java** 契约，勿臆造。

```
❌ 错误：用户说「把搜索改快一点」，就直接加缓存 + 索引 + 异步
✅ 正确：先问清楚——响应时间？首屏？还是输入防抖？每种方案代价不同
```

## 2. 简洁优先

**用最少代码解决问题。不过度推测。**

- 不加需求之外的功能
- 不为单次使用的代码创建抽象
- 不加未要求的「灵活性」或「可配置性」
- 不为不可能发生的场景写错误处理
- 200 行能搞定的事写成 50 行

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

### 与项目规则的关系

Blue Dock 已有明确的抽象边界（api / ui / app / apps），这些是**必要的**架构约束。简洁优先适用于**这些边界之内**的代码——不要在单个函数或组件内过度设计。

## 3. 精准修改

**只碰必须碰的。只清理自己造成的烂摊子。**

- 不要「顺手改进」相邻代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格
- 如果注意到无关的死代码，提一下——但不要删
- 删除**因你的改动**而不再使用的 import / 变量 / 函数

**检验标准：** 每一行修改都应该能直接追溯到用户的需求。

## 4. 目标驱动执行

**定义成功标准。循环执行直到验证通过。**

| 不要…          | 转化为…                                |
| -------------- | -------------------------------------- |
| 「加个验证」   | 「先写无效输入测试 → 让测试通过」      |
| 「修这个 bug」 | 「先写复现测试 → 确认失败 → 修到通过」 |
| 「重构 X」     | 「确保重构前后所有测试都通过」         |

多步骤任务先列计划：

```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
```

```
❌ 错误：「我来审查并改进代码」
✅ 正确：「跑 typecheck → lint → lint:circular → test → 全部通过才算完成」
```

## 5. Blue Dock 补充

- 改完同步 `docs/`；接口变更先改 blue-dock-java
- 功能完成后对该功能**全量**回归，不只测本次 diff
- 鉴权 / 上传 / 会议 / 微应用 / Token 路径提高严谨度
- 禁止空 catch、失败当成功、鉴权失败静默跳过

## 反模式速查

| 原则         | 反模式                       | 修正                                     |
| ------------ | ---------------------------- | ---------------------------------------- |
| 编码前思考   | 默默假设字段、路径、范围     | 明确列出假设，查契约或请求澄清           |
| 简洁优先     | 单次逻辑搞出策略模式继承体系 | 一个函数，等真正需要再重构               |
| 精准修改     | 修 bug 时顺手改全文件风格    | 只改导致 bug 的那几行                    |
| 目标驱动执行 | 「我来审查并改进代码」       | 「写复现测试 → 确认失败 → 修到测试通过」 |
