# Karpathy 行为准则

四大原则用于指导代码编写、审查和重构，减少 LLM 常见编码错误。

**权衡：** 偏向谨慎而非速度。简单任务自行判断。

## 1. 编码前思考

**不要假设。不要隐藏困惑。呈现权衡。**

- 明确陈述假设。不确定就问。
- 多种理解存在时全部列出，不默默选择。
- 有更简单方案时说出口，该反驳时反驳。
- 不清楚的地方停下来，指出困惑点。
- API 不确定先查 blue-dock-java 契约。

## 2. 简洁优先

**最少代码解决问题。不过度推测。**

- 不加需求之外的功能。
- 不为单次使用创建抽象。
- 不加未要求的「灵活性」或「可配置性」。
- 不为不可能的 scenario 写错误处理。
- 200 行能写 50 行就重写。

**检验：** 资深工程师会觉得过于复杂吗？如果是，简化。

## 3. 精准修改

**只碰必须碰的。只清理自己造成的烂摊子。**

- 不顺手改进相邻代码、注释或格式。
- 不重构没坏的东西。
- 匹配现有风格。
- 删除因你改动产生的孤儿代码，但不碰预先存在的死代码。

**检验：** 每行改动都直接追溯到用户需求。

## 4. 目标驱动执行

**定义成功标准。循环验证直到通过。**

| 指令式     | 目标式                          |
| ---------- | ------------------------------- |
| 「加验证」 | 「写无效输入测试 → 让测试通过」 |
| 「修 bug」 | 「写复现测试 → 确认失败 → 修」  |
| 「重构 X」 | 「重构前后测试全部通过」        |

多步骤任务列出验证计划：

```
1. [步骤] → 验证: [检查项]
2. [步骤] → 验证: [检查项]
```

## 在 Blue Dock 中的应用

- **精准修改** 意味着改 messenger bug 时不动无关 feature
- **简洁优先** 意味着不要为单端差异在 api 层堆抽象
- **目标驱动** 意味着修完跑 `bun run typecheck && bun run lint && bun run test`
- **编码前思考** 意味着改 api 层之前确认不会破坏 app / ui 调用方

详见 [behavior.md](../../rules/behavior.md)。
